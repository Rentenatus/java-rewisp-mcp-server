| B-01 | GBR:130-136 (call :73) | HIGH | The task allowlist checks every argument without a leading `-`. On the call `dependencies --configuration compileClasspath`, `compileClasspath` is such an argument, is not in the allowlist and triggers `GOAL_NOT_ALLOWED`. `GradleBuildResolver.resolve` therefore fails for every project with a wrapper before the classpath is resolved. The edit tools swallow the exception (e.g. AddFieldTool:208), so Gradle support is effectively dead. The tests mask this: GradleBuildResolverTest:106-109 accepts `TASK_NOT_ALLOWED` (this code does not exist), the integration tests are `@Disabled`. | Check tasks (first non-flag argument) and values of `--configuration` separately. |
| B-02 | GBR:309-356, :244 | HIGH | `parseGradleClasspath` returns Maven coordinates (`g:a:v`) from the dependency tree, not JAR paths. `ProjectBuildHelpers.enrichClasspathFromBuild` (:164) and `OpenRewriteEngineImpl` (:69-72) pass these strings as classpath to Spoon and OpenRewrite. These entries are not valid classpath entries, type attribution stays incomplete. The `treePattern` (:337) also takes the requested version before `->` instead of the resolved one and does not detect `project :x`. | Output JAR paths via an init-script task or the Gradle Tooling API, do not parse the tree. |
| B-03 | GBR:280, :295 | MEDIUM | `gradlew properties` outputs lines in the format `name: value`, the regexes expect `name=value`. `moduleId` therefore always falls back to the directory name, `languageLevel` is always "17" (:302). A project with `sourceCompatibility: 21` still reports 17. | Change regex to `^name:\s*(.+)$` resp. `^sourceCompatibility:\s*(.+)$`. |
| B-04 | GBR:154-166 | HIGH | Gradle reads the output with blocking `readLine()` until EOF and only calls `waitFor(timeout)` afterwards. If the process hangs without further output (download, lock on `~/.gradle`), `readLine` blocks forever and the timeout never applies. The MCP tool thread blocks indefinitely. Maven solves this with a reader thread (MBR:134), Gradle does not. | Use a reader thread like in MBR, or redirect output to a file and call `waitFor` first. |
| B-05 | MBR:156, GBR:159/169 | MEDIUM | `destroyForcibly()` on Windows only terminates the direct process (`cmd.exe` of `mvn.cmd` resp. `gradlew.bat`), not the child JVM. After timeout or output limit the Maven/Gradle JVM keeps running as a zombie, holds locks in `~/.m2` resp. `.gradle` and blocks subsequent calls. | Iterate `process.descendants()` before the kill and terminate them with `destroyForcibly()` as well. |
| B-06 | MBR:63-77, :86 | HIGH | The Maven resolver writes `.effective-pom.xml` and `.maven-classpath.txt` permanently into the project root. `ProjectManager.ensureBuildContext` (PM:314) is not synchronized. Two parallel calls (two edit tools, watcher reload) run on the same file: one deletes it (:78), the other reads it via `readSafe` as an empty string. The result is a silent, empty classpath that stays in the cache. The files also appear in the workspace and can trigger the watcher as a change. | Use `Files.createTempFile` per call and serialize `ensureBuildContext` per project via `computeIfAbsent` or a lock. |
| B-07 | MBR:84, :193-219 | HIGH | For multi-module projects `parseModules` always returns exactly one module: name = directory name, `languageLevel` hardcoded "17" (:216), `effectivePom` ignored. `dependency:build-classpath` runs in the reactor for each module against the same absolute `-Dmdep.outputFile`, the last module overwrites the others. The root's classpath is therefore unreliable. MavenMultiModuleIntegrationTest:96-107 only checks `size() >= 1`. | Own output file per module (`${project.build.directory}`-relative) and build modules from `<modules>` resp. the effective POM. |
| B-08 | MBR:165 | LOW | The reader thread aborts at `output.length()+line.length()+1 > maxBytes` (:140), the check after process end uses `output.length() >= maxBytes`. On abort the length is usually smaller than `maxBytes`, `OUTPUT_LIMIT` is not reported. Instead `BUILD_FAILED "Maven exit code 1"` comes (from `destroyForcibly`). | Set an `AtomicBoolean truncated` in the thread and evaluate it afterwards. |
| B-09 | build/PomUtils.java:56-59, :49-52 | MEDIUM | `resolveParentPomPath` returns `../pom.xml` even when the POM has no `<parent>`. `<relativePath/>` (empty, common with Spring Boot: "do not look in the filesystem") does not match the pattern, the default fallback applies anyway. A relativePath pointing to a directory returns the directory instead of the `pom.xml` (`Files.exists` is enough). Consequence: `check_project_dirty` invalidates unrelated projects (`CheckProjectDirtyTool:335-352`) that happen to lie under the same POM. | Only look when `<parent>` is present, respect empty `<relativePath/>`, append `pom.xml` for directories and check `isRegularFile`. |
| B-10 | tools/ProjectRefreshBuildTool.java:61-74 (among others :69-74) | LOW | The output is built with `"\\n"` (backslash plus n as text), other tools use `"\n"` (e.g. CheckProjectDirtyTool:148). The Markdown table therefore appears as one line with literal `\n`. | Replace `"\\n"` with `"\n"`. |
| B-11 | GBR:263-272 | LOW | `filterSourceRoots` checks the absolute path with `contains("/main/")` resp. `"/test/"`. If the project lies under `C:\work\test\proj`, all main roots also land in `testSourceRoots`. `build/generated/...` matches neither and is missing from both sets, `generatedSourceRoots` stays `Set.of()` (:253). | Classify relative to `projectRoot`. |
| B-12 | GBR:97-121 | LOW | `findGradleExecutable` chooses `gradlew.bat` solely by `Files.exists`, also under Linux/macOS. This leads to `IO_ERROR`. | Check the OS and use `gradle` resp. `gradle.bat` as fallback when the wrapper is missing. |
